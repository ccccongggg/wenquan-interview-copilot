# 问全 0.5.6 执行文档：声音身份与临时人物档案

日期：2026-10-18  
基线：问全 0.5.5，`feat/0.5.5-guided-suggestions`  
文档状态：待实施。本文件仅定义需求、实现方案与验收条件，不表示功能已经实现。

## 1. 需求共识

本轮解决“谁在说话”的归属问题，减少依赖语言模型反复判断主持人和嘉宾，给后续追问提供可靠的人物来源。

采用以下方式：

1. 主持人提前录入并保存自己的声纹，仅标记为“主持人”，无需提取职业等背景属性。
2. 主持人填写本次被访谈者人数。界面明确此数字不包含主持人。
3. 开场请被访谈者依次自我介绍，系统自动采集声音、建立本场临时人物档案。
4. 从自我介绍中尝试提取本人明确表达的姓名、职业、项目职责等信息，再与该段声音对应的人物档案关联。
5. 提取不到背景信息，仍可标记为“被访谈者 1”“被访谈者 2”等，正常进行访谈。
6. 主流程不要求主持人逐个手动确认身份、职业或声音对应关系。人工纠正仅为异常情况下的可选入口。
7. 正式访谈中，转写与声音匹配并行进行，匹配结果绑定到对应发言，再用于追问和归纳。
8. 首版按单人依次发言设计，不承诺处理抢话、多人重叠或复杂嘈杂场景。

### “自动确认”在本方案中的含义

系统判断某个声音属于哪个本场人物，并建立可复用的对应关系，不等于核验真实身份。

例如：声音 A 与一段自我介绍对应，内容为“我负责产品设计”，系统可以形成“被访谈者 1，背景：负责产品设计”。没有介绍或介绍不清楚时，只建立“声音 A → 被访谈者 1”。

人物区分成功，不以姓名、职业提取成功为前提。后续补充姓名或职责，不创建新的参与者编号。

## 2. 当前问题与本轮目标

| 当前问题 | 本轮目标 |
| --- | --- |
| 语言内容不足以稳定区分主持人与嘉宾 | 使用主持人声纹和本场人物声音档案作为主要归属依据 |
| 未知角色可能触发串行模型识别，影响追问响应 | 将声音匹配与转写并行，移除常规流程中不必要的角色推断等待 |
| 多位嘉宾统一归为 guest，容易混淆回答来源 | 增加独立参与者 ID，并将原话、回应和摘要引用关联到具体人物 |
| 嘉宾身份信息不完整 | 支持仅用编号正常运行，背景信息可缺省 |

注意：0.5.5 已绑定的声音会复用角色，并非每段发言都会重新调用角色识别。本轮优化针对未绑定声音、跨流重连与多人归属等实际缺口。

## 3. 产品操作流程

### 3.1 主持人声纹设置

在设置中提供“主持人声音”入口：

- 首次使用，采集主持人独立、清晰的讲话音频。
- 由声纹服务检查采样质量与有效时长；不足时提示继续说，不按固定录音时长保证注册成功。
- 注册成功后保存主持人声纹标识和必要配置，支持重新录入和删除。
- 优先使用正式访谈时的设备与收音方式录入。
- 不提取主持人的职业、性格、年龄等属性。

没有可用声纹时，界面明确提示“主持人声音未就绪”。可以引导现场补录；如提供降级模式，必须明确其能力不同，不能显示为声纹已注册。

### 3.2 设置人数

准备页新增“被访谈者人数”，默认 1，首轮产品目标可设为 1–5 位嘉宾，另加 1 位主持人。

这是期望人数，不是识别出的事实人数。尚未讲话的人无法仅靠声音发现。实际人数不一致时允许修改，不能为了凑足人数而拆分同一个人的声音。

### 3.3 开场自动建档

主持人点击“开始开场介绍”，录音持续运行，并提示大家依次介绍自己。

系统自动完成：

1. 根据主持人声纹识别主持人发言。
2. 对其他稳定且可区分的声音建立本场参与者编号。
3. 将该人物的介绍文本用于一次背景提取；只提取本人明确陈述的信息。
4. 以卡片展示自动结果，例如：
   - 主持人：声音已匹配。
   - 被访谈者 1：负责产品设计。
   - 被访谈者 2：背景未填写。
5. 声音样本不足、存在混叠或匹配不确定时，显示“声音采集中／待区分”，不生成虚假确定结果。

不得根据说话先后、声音高低、单个疑问句或性别印象直接认定主持人。

### 3.4 进入正式访谈

有可用人物区分结果后，主持人可点击“开始正式访谈”。这只是阶段切换，不是逐人审核身份。

若仍有未就绪人物，清楚提示当前进度；允许明确进入“仍有声音待识别”的访谈状态，继续采集，但不能把待识别片段当成确定人物的事实。

开场与正式访谈优先沿用同一音频流，避免切换阶段时无谓重启识别。开场记录可保留为单独阶段，默认不触发现场追问，也不混入项目经历等正文事实。

### 3.5 访谈中

- 发言展示人物编号或别名，并可附带简短背景。
- 同一个人多次讲话，保持同一参与者 ID。
- 背景提取失败不阻塞转写、声音区分或已有访谈操作。
- 发现新声音时保持未知或建立待识别人物；稳定证据充分后再新增嘉宾编号。
- 超出预设人数时提示人数不一致，不强行归入现有嘉宾，也不自动修改预设人数。
- 人工更正人物关联是可选入口，更正后重新检查受影响的事实、问题回应与归纳。

## 4. 技术方案

### 4.1 分清三种能力

| 能力 | 作用 | 不能替代的能力 |
| --- | --- | --- |
| ASR 说话人分离 | 对音频分段并返回本次流内的声音编号 | 编号本身不是持久声纹，也不代表主持人或真实人物 |
| 声纹提取与匹配 | 匹配预注册主持人及本场人物声音档案 | 不自动得出姓名、职业等背景 |
| 介绍文本理解 | 提取本人明确说出的背景信息 | 不能仅凭内容替代可靠的声音身份匹配 |

必须接入可验证的声音特征提取与匹配能力，才能宣称支持真正声纹。不得将现有 speaker_id 重命名为 voiceprint，就宣称已完成跨流声纹注册与识别。

### 4.2 处理流程

音频采集后分为两条并行路径：

- 转写路径：音频 → ASR → 带时间范围的文字。
- 人物路径：音频 → 语音活动及说话人分段 → 声音特征提取 → 主持人／本场人物匹配。

两条路径根据流 ID、片段 ID 和时间范围合并，生成带人物身份的发言，再提供给访谈分析。

如果上游服务直接提供可靠的统一结果，可复用同一服务输出，不要求重复搭建两套模型。无论采用哪种方式，都要保留足够的来源信息以核对文字与人物是否对应同一段音频。

文字先到时可先显示“人物确认中”，人物匹配完成后补齐。人物相关事实和回应归档必须使用可靠归属；不要无限等待，更不能超时后默认认定为主持人或某位嘉宾。

### 4.3 匹配规则

- 匹配主持人既有声纹，并与本场嘉宾声音档案进行区分。
- 使用经过标注样本校准的相似度阈值、候选间差距及连续证据；不得以固定通用阈值承诺准确率。
- 短促的“嗯、对、好”可暂缓归属，不能据此新建或覆盖人物档案。
- 避免用不确定、混叠或明显噪声片段更新声纹模板，防止错误扩散。
- 不确定时保留 unknown。不能把“未匹配主持人”直接等同“已识别出某位嘉宾”。
- ASR 修订、人物更正与迟到结果需要版本检查，过期结果不得覆盖新状态。

### 4.4 背景提取规则

- 只在介绍阶段及后来明确补充个人资料时触发，不为每段话重复提取职业。
- 输出可为空；失败不影响参与者编号。
- 背景字段保留对应原话、片段和来源人物。
- 区分本人介绍、主持人介绍与转述他人，不将“我的同事是设计师”写为本人是设计师。
- 背景信息用于辅助追问，不作为身份认证或已核实事实。
- 主持人只保留主持人角色，不进入嘉宾职业属性提取流程。

### 4.5 断线、重连与恢复

- 业务参与者 ID 独立于 ASR 的 speaker_id，不能假设重连后编号保持一致。
- 真正声纹匹配可用于新音频流与本场人物的重新对应。
- 尚无可靠匹配时，重新采集或暂标未知，不直接继承旧流的编号关系。
- 保留已保存的文字与人物档案；匹配失败不能清空历史访谈。

## 5. 数据结构要求

新增概念应与现有 host／guest 角色分开：

| 对象 | 必要字段或信息 |
| --- | --- |
| 主持人档案 | 本地档案 ID、声纹服务标识、声纹引用、注册状态、版本、更新时间 |
| 本场参与者 | participantId、role、默认编号、可选别名、可选背景、建档状态、声纹引用 |
| 发言片段 | segmentId、streamId、时间范围、speakerId、participantId 或空值、归属状态及来源 |
| 背景证据 | 属性内容、来源人物、原话、segmentId |
| 访谈状态 | 预设嘉宾人数、开场／正式阶段、本场人物集合 |

role 继续表达 host／guest／unknown；participantId 表达具体是哪个人。

例如，嘉宾 1 和嘉宾 2 的 role 都为 guest，但 participantId 必须不同。后续修改名字不改变 participantId。

## 6. 多人访谈中的业务改动

仅在转写上增加人物标签不够，必须同步处理：

- 实时分析上下文携带参与者 ID 和与本次问题相关的嘉宾背景。
- 主持人的问题可以有明确目标嘉宾，也可以面向全体；无法确定时不强行猜测。
- 嘉宾 2 的回答不能自动视为嘉宾 1 已回应；可记录为另一人补充。
- 事实与引用保存来源参与者，多位嘉宾的不同说法不能无说明地合并。
- 眼镜问题需要区分目标人物时，附带简短人物标签，不堆叠整份背景档案。
- Markdown、问题历史和会后归纳保留人物来源，旧版无人物信息的记录保持兼容。
- 人物归属修订后，撤回或重新检查受影响的派生结果，保留原始转写及修订记录。

## 7. 服务选型与接入前置检查

实施前必须确认：

1. 当前音频采集接口输出的编码和分块是否可供声纹服务使用。
2. 当前 Agent Plan ASR 接口实际支持哪些说话人、声纹或实时注册能力，不能直接套用其他产品端点的参数。
3. 声纹能力是否支持多人依次发言、主持人预注册和本场嘉宾动态建档，而非仅支持一句话内单主说话人的识别。
4. 是否能取得匹配分数、未知结果、分段时间和重连所需信息。
5. 音频解码、模型部署、网络请求、服务额度与并发限制是否符合实际运行条件。

若当前服务不能满足，选择独立声纹服务或可实时运行的专用模型。该选择需要用真实设备录音比较，不在未验证前固定供应商或承诺延迟。

背景资料：

- 火山说话人分离说明：https://docs.volcengine.com/docs/DoubaoVoice/speaker-separation?lang=zh
- 说话人分离与身份识别区别：https://www.pyannote.ai/blog/speaker-diarization-vs-recognition-vs-identification

以上为选型参考，不代表这些接口已在问全中接入或当前账号已获得权限。

## 8. 性能策略

- 转写与人物匹配并行，不为每段发言串行调用语言模型识别 host／guest。
- 介绍背景提取异步执行，失败或较慢不阻塞基本人物区分。
- 主持人和嘉宾已有可靠绑定时复用，不重复建立人物档案。
- 同时记录采集、转写、人物就绪、分析完成和眼镜显示确认的时间，定位端到端延迟。
- 既比较速度，也比较归属错误率；不把“越快就一定越准确”作为设计前提。
- 不以缩短音频到无法可靠匹配为代价追求更快结果。

## 9. 存储与数据边界

- 主持人声纹用于长期复用，提供重新录入与删除入口。
- 嘉宾声音档案默认仅用于本场，不自动建立跨场人物库或实名档案。
- 将“结束后是否保留、恢复访谈需要保留多久、是否需要删除上游声纹”作为明确产品配置，不以“临时”一词替代真实清理策略。
- 采集和使用声音特征前说明用途并取得参与者同意；长期保留嘉宾声纹需单独选择。
- 原始音频、服务端声纹 ID、匹配凭据和上游密钥不进入普通 Markdown 导出或调试日志。
- 声纹特征即使不是原始录音，也按敏感数据处理；上游和本地存储策略须一致说明。

## 12. 验收条件

### 功能验收

- [ ] 主持人可注册、复用、重新录入和删除真实声纹。
- [ ] 主持人不需要提供职业等背景属性。
- [ ] 开场多位嘉宾依次介绍，自动建立不同人物档案，不要求逐人手动确认。
- [ ] 无姓名或职业的嘉宾，仍以编号正常参与后续流程。
- [ ] 背景识别错误不会使两个人合并，背景提取失败不会阻塞转写。
- [ ] 同一嘉宾跨多段发言保持同一 participantId。
- [ ] 短应答、陌生声音、人数不一致和重叠讲话不会被强行确定归属。
- [ ] 重连后通过可靠匹配恢复人物；不能仅复用旧 speaker_id。
- [ ] 嘉宾之间的原话、问题回应、摘要引用和导出不串人。
- [ ] 不确定归属不被写成主持人或某位嘉宾的确定事实。
- [ ] 开场介绍不触发正式现场追问，不被误写成项目事实。
- [ ] 旧版记录、分块存储、暂停与结束流程回归通过。

### 效果验收

使用经同意采集并人工标注的真实设备录音，覆盖一位主持人与 1、2、5 位嘉宾依次发言。分别记录：

- 主持人误判为嘉宾、嘉宾误判为主持人的情况。
- 嘉宾之间串人的情况、未知比例和建立稳定归属需要的有效音频量。
- 介绍背景提取的错误与缺省情况。
- 与 0.5.5 对比的转写延迟、人物就绪延迟和眼镜提示 P50／P95 延迟。
- 暂停、重连、音频修订后的身份连续性。

测试先报告实测结果，再确定上线门槛。自动测试和合成音频不能代替真实音色的识别效果验收。

## 13. 本轮边界

本轮不实现真实姓名认证，不推断性格或其他未经本人表达的属性，不承诺复杂重叠语音识别，也不以声纹归属改进替代 ASR 文字准确率优化。

此前讨论的长回答重复补题、目标完成判断和澄清问题属于相关但独立的迭代内容；除身份归属所必需的联动外，不混入本轮交付范围。

## 14. 完成定义

0.5.6 的完整目标是：主持人声音可提前复用；嘉宾通过开场发言自动形成可区分的临时人物档案；背景信息有则关联、无则编号；正式访谈不依赖每段语义猜测角色，人物来源可以核对和纠正。
