## 1. 判断

这副眼镜可作为声音采集设备，通过手机联网，把音频送到服务端完成转写和人物识别。现有 SDK 足以支撑这种架构，没有查到必须更换眼镜的接口障碍。

但“具备可实现的技术路径”不等于“现有设备在真实现场已经达到目标”。主持人声音复用、嘉宾开场自动建档、断线后稳定对应、五位嘉宾加一位主持人，以及现场噪声和距离影响，仍须真人设备测试。

目前的主要缺口是声音身份处理链路的选择、接通与效果验证，不能直接判断为眼镜不支持，也不能因缺少独立服务配置就让用户自行寻找供应商。

## 2. 为什么眼镜录音后，不能只让目前的大模型提取声纹

用户提出的思路正确：眼镜负责采集，外部模型负责处理。这里需要区别模型的任务。

| 输入与处理 | 能得到什么 | 不能直接保证什么 |
| --- | --- | --- |
| 原始音频 → 转写服务 | 文字、部分时间范围、可用时的说话人编号 | 编号对应现实中的谁、跨流是否仍为同一个人 |
| 转写文字 → 当前问答模型 | 从“我是主持人”“我负责研发”等原话中理解角色和背景 | 文字已经不含音色，不能据此重新提取声音特征 |
| 原始音频 → 专门的声音身份模型 | 可匹配的声音特征，或服务商提供的声纹 ID 与匹配结果 | 不经实际采样验证的准确率、拥挤现场的稳定性 |

当前项目的 `server/model.mjs` 使用文本 messages 接口发送访谈资料，`profiles/volc-agent-plan.env.example` 指向 `deepseek-v4.1-flash`。官方当前接入配置列明文本/图像输入，没有列出音频输入；不能把它当作已具备声纹提取能力。依据：[Agent Plan 模型配置](https://docs.volcengine.com/docs/ark/agent-plan-personal-pi?lang=zh)。

如果采用有音频能力的模型，也应核对它是否提供稳定的说话人匹配或特征接口；“能听懂音频、描述音色”并不自动等于“提供可复用声纹”。产品中仍可完全隐藏这些技术差异，用户只做声音录入和访谈。

## 3. 本机实际证据

1. SDK `PhoneSDK/docs/web-plugin/api-reference.md` 的 Native glasses audio 部分，提供 `gm.audio.openCapture()` 和实时二进制 `ReadableStream<AudioChunk>`，包含帧边界、时间信息与丢帧信息。
2. `PhoneSDK/packages/web-sdk/src/index.d.ts` 明确音频为 Opus、16 kHz、单声道，并支持多种拾音模式。拾音模式名称不代表已测得的收音半径或多人准确率。
3. 项目 `web/recording.js` 已将原生 Opus 封装为 Ogg 并发送至 ASR。音频格式可在服务端解码为 PCM/WAV，不必要求眼镜原生返回 WAV。

## 4. 官方现成能力及限制

火山官方存在声纹注册管理接口，接受 5–30 秒的 WAV、PCM 或 MP3 音频，可管理已注册声纹。因此可以研究复用同一供应商，不能预设用户必须购买另一家服务。眼镜输出的 Opus/Ogg 需要经过格式转换，不能原样当作官方声纹注册格式提交。依据：[声纹注册/管理接口](https://docs.volcengine.com/docs/DoubaoVoice/voiceprint-registration-management-api?lang=zh)。

官方将流式说话人分离、短音频声纹匹配和录音文件声纹匹配分别描述；其中流式短音频匹配限定单说话人，不适用于多人分离。因此不能仅给现有连续访谈请求加一个声纹参数，就宣称实现主持人和所有嘉宾的实时身份识别。可研究先分离单人片段再匹配，但新增调用、延迟、服务权限与费用都需验证。依据：[说话人分离最佳实践](https://docs.volcengine.com/docs/DoubaoVoice/speaker-separation?lang=zh)。

当前 Agent Plan 文档列出 ASR/TTS 和专属接入信息，没有找到足以确认本账号套餐包含声纹注册管理的证据。未实测前保留“权限及计费待核对”；不把通用产品接口的功能和额度自动套到 `/plan/` 地址。依据：[Agent Plan 语音模型](https://docs.volcengine.com/docs/ark/agent-plan-personal-voice-model?lang=zh)。

## 5. 三条可选路径

| 路径 | 用户体验 | 放弃或增加的内容 | 判断 |
| --- | --- | --- | --- |
| A：完整目标，增加声音身份处理 | 主持人提前录入；嘉宾依次介绍自动建档；跨流按声音重新匹配 | 接通专门模型或官方身份接口，校准阈值，真实设备验证 | 技术路径可行，尚未证明现场效果；不是仅换提示词 |
| B：本场自动识别，沿用当前 ASR | 主持人每场说一句明确开场，嘉宾依次介绍；流内声音编号绑定本场人物，背景从原话补充 | 不保留可复用主持人声纹；重连需重新介绍，未知时少量人工更正 | 最接近现有能力、改动较少的备选；仍须真人测试 |
| C：主持人/嘉宾两类，保留原话 | 一对一可主要靠语境分角色；多人原话完整保存，人物不确定则待识别 | 不承诺多位嘉宾自动精准归因 | B 现场效果不足时的最终保底 |

路径 B 的正常过程不要求逐个人工确认。系统根据明确的开场原话和同一流内声音编号关联人物；“第一段就是主持人”“编号0必然主持人”都不可作为规则。出现串号、重连、身份不明时才提示补充介绍或人工更正。不能将该路径称为已注册声纹。

路径 A 也可以自部署声音身份模型，不一定另买云服务。官方开源项目 [3D-Speaker](https://github.com/modelscope/3D-Speaker) 提供说话人验证、特征提取和分离推理路线，能作为候选。选择它需额外部署模型运行环境并测试设备音频；本轮没有下载权重、安装相关依赖或宣称速度、准确率已验证。

## 6. 推荐推进顺序

优先保留现有眼镜与 ASR，用一对一真实访谈核对收音、声音编号和自动开场映射，再逐步扩到两位和五位嘉宾。若用户希望尽快有可用体验，路径 B 最适合作为第一阶段；若主持人跨场复用和跨流身份稳定是必须项，则走 A，B 作为故障回退。

后续验证必须分别记录：转写可用时延、人物就绪时延、眼镜显示时延；同一人物跨轮/跨流是否换号；甲的原话是否被记成乙的经历；重叠和短句是否保留未知。五位嘉宾不包含主持人，最终六人场景必须单独验收，不能从双人合成测试外推。

当前不能给出真人六人准确率、可用距离、平均端到端时延或成本结论。
